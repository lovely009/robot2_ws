# 墙钟闭环定位与收敛记录（2026-11-01）

本轮停止重复等待墙钟测试偶然全绿。UI 已交付；本地整合分支仍不可合 dev 或用于真实设备。所有设备、总线和标定均为虚构测试 fixture；未连接硬件、推送或部署。

## 已定位并修正

1. 原 SIL 把虚拟 MCU 和 supervisor 放在同一个单线程执行器，不符合生产进程边界。现为独立 supervisor、bridge、JTC 进程，虚拟 MCU 自有执行器，使用真实固件 gate/kernel、CAN 编解码和调度及有状态模型。
2. 同一有效所有权接续标准目标时不再强制重启 JTC；新所有权仍清退旧控制器。目标上下文同时绑定 MCU 租约代数，解除武装后重新武装不能恢复旧计划。
3. trace 证明第二目标校验阻塞 50Hz 转发：原 JTC 样本间隔约 20ms，某样本到私有转发面年龄 11.227ms，旧截止 tick=8282，新包 tick=8284 到达。轨迹校验现放在单独工作线程并复用结果；所有权状态仍由原执行器管理。校验完成重新核验授权，不在工作线程发送运动或使能。
4. 新鲜目标在原厂商使能整定窗内恢复软停时，执行状态正确回到 ENABLING；不重启或缩短整定窗，不提前发送 MIT，缓存旧目标不能到达此恢复路径。定向固件回归保留原始 30/100ms 到期断言。
5. 取消在控制器准备阶段返回 CANCELED；迟到准备回调不能再发送目标。受租约 facade 取消标准 Action 时使用同一个 UUID 的标准 CancelGoal 转移，不把普通标志当成服务器的 CANCELING 状态。
6. A 的 3 项旧运行夹具、B 的 2 个运行模式都迁移为共享原生固件 fixture。保留握手、错误授权、完成/反馈、取消、独立停机 ACK、旧目标不复活、配置命名空间、手动/动作/重力调试、客户端消失及控制循环退出断言；没有删断言或调整安全期限以求通过。自动 REPORT 的 request_id=0 是委托 bridge 分配的哨兵，测试同时检查非法高位被拒绝、实际线上查询 ID 和关联设备终态。

## 剩余时延不是“只由 CPU 节流”这一结论

固定四核实验期间，外层 CPU 配额为4核/100ms；计数增加1次节流，累计约37067µs。全运行 trace 出现54.485ms模拟服务空档和33.209ms原始主机样本间隔，但这些最大值包含故障后的传播过程，不能全部当作初始原因。

按“发送目标至首次软停”截取的故障前片段：原始 JTC 最大连续生成间隔23.157ms，私有转发面样本年龄最大8.949ms，线上相邻包最大28.187ms；虚拟 MCU 服务空档14.451ms。最后一包 tick=7556、绝对截止=7580，下一次服务恢复前已错过期限。另一个默认调度片段也记录13.892ms模拟服务空档。它们说明共享普通 Linux 调度下，模拟器和主机链路均没有足以验收的时延上界；不能证明所有停顿均由节流引起，也不能拿单次成功证明稳定实时性。

原生固件输出计数使用 MCU 虚拟毫秒时钟；墙钟暂停后的模拟追赶不能作为真实 CAN 物理间隔200Hz或真实停机延迟验收。USB CDC12Mbps、真实CAN拥塞、WCET、抱闸和实机装配均未覆盖。

## 最小下一步决定

建议保持现有30/100ms安全期限，将连续运动稳定性验收放到能测量并约束调度上界的隔离环境。必要条件是“连续目标生成间隔 + 新目标从生成到 MCU 受理的延迟”小于原始30ms窗口；50Hz名义周期20ms只剩不足10ms的总余量，还要扣除时钟换算、队列和传输开销。

若要求在普通非实时主机也能吸收更大抖动并持续运动，需要另行决定是否评审带绝对执行时间的有界前瞻目标；这会涉及现有“旧目标30ms停”的执行语义，不能擅自实现。本轮没有新增前瞻/滚动协议、放宽门限、把收到时间重当生成时间或自动使能。

这不是连接、上传或权限被拒的问题。当前缺口是稳定墙钟时延验收及上述运行组合，dev合入须继续等待，源码和证据已独立保全。
