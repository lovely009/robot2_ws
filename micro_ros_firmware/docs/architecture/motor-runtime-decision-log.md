# micro-ROS 电机运行时架构开发基线

> 对应 ADR：[ADR 0007：micro-ROS 采用发现驱动的聚合式电机运行时](../adr/0007-micro-ros-discovery-driven-motor-runtime.md)。
> 本文是 `micro_ros_firmware` 重构的开发基线；旧台账中的逐条讨论已归并，不要求开发者逐条回看。
> 原始基线日期：2026-09-04。
>
> **当前适用性（2026-09-23）**：本文早期设计仍作为领域与行为基线；当前控制边界为 2 ms/500 Hz，服务周期为 1 ms。TX 队列、协议聚合和物理提交分别归 `lib/fdcan`、`lib/motor_protocol` 与 `lib/motor_tx_router`；SAVE 两阶段状态归纯 C `lib/save_transaction`，ROS/W25 适配仍归 `param_bridge`/`storage_task`。本轮增加 host 契约覆盖；台架与最大规模开放项统一见[开放项](../../README.md)。

## 1. 目标和原则

系统由 STM32H723 上的 micro-ROS 固件控制约 40 台 Vaxor/CERB 外置电机，使用
FDCAN1、FDCAN2、FDCAN3，三路均为 CAN-FD 仲裁段 1 Mbps、数据段 5 Mbps。电机 ID
在系统内唯一；电机可动态上线、离线和热插拔。

开发只遵守以下原则：

- MCU 不维护“每台电机一行”的固定安装表，只维护运行时注册表。
- 固件和上层各维护一份按型号组织的 `MotorModelProfile`；上层维护
  `motor_id → joint_name`、方向、零位和关节语义。
- 两类电机默认 MIT 模式。协议字节只存在于对应协议适配器中。
- 控制命令边界为 2 ms/500 Hz；上行运动状态按 50 Hz 发布，其他域节拍见工程
  README；`motor_rt_task` 以 1 ms 服务节拍运行。
- FDCAN ISR 只接收原始帧入环形缓冲；`motor_rt_task` 是唯一解码和正常发送的业务所有者。
- ROS 聚合消息不能直接当 CAN 帧发送；实时任务必须经过协议适配器组帧和调度。
- 实时路径使用固定容量和静态内存，不在 ISR、控制和 CAN 发送路径动态分配。

## 2. 总体数据流

```text
ROS 2 controller
  └─ ros2_control position/velocity/effort interfaces
       └─ upper hardware interface: joint ↔ motor_id
            ├─ MotorCommandArray (100 Hz, complete snapshot)
            ├─ MotorPolicy / MotorConfig (low frequency)
            └─ micro-ROS Agent / USB CDC
                         │
                    micro_ros_task
                         │ 只校验消息、写 mailbox、发布状态副本
              command/config mailbox
                         │
                   motor_rt_task (1 ms)
              ┌──────────┼──────────┐
              │          │          │
        registry     safety       protocol adapters
              │          │       Vaxor / CERB
              └──────────┴──────────┘
                         │
                 FDCAN1 / FDCAN2 / FDCAN3
                         │
                    外置电机
```

上行反馈反向经过 `motor_rt_task`：原始 CAN 帧 → 适配器解码 → 运行时状态副本 →
micro-ROS 状态消息。拓扑变化和配置结果走低频消息，不塞进 100 Hz 运动状态。

## 3. 运行时流程

### 3.1 启动、发现和热插拔

1. 初始化三路 FDCAN、静态缓冲、协议注册表和运行时注册表。
2. 启动 `motor_rt_task` 后进入发现窗口；Vaxor 用自身 20 ms 状态识别型号，CERB
   用反馈/管理读取识别身份。CERB 的 `0x080 SYNC` 只用于发现、重连和热插拔探测。
3. 身份确定后选择固件 `MotorModelProfile`，读取或确认设备能力；失败则保持禁能并
   发布原因。
4. 发布一次全量 `MotorTopology`。设备再次上线、离线、身份变化或能力冲突时更新
   拓扑并发布事件。
5. 只有完成识别、能力校验、策略授权和新的完整命令快照后，电机才允许进入 `ACTIVE`。

### 3.2 1 ms 服务节拍

`motor_rt_task` 每 1 ms 做有界工作：

1. 从 FDCAN1/2/3 RX 环逐帧取出原始帧。
2. 按总线和 CAN ID 找到注册表项，交给协议适配器解码。
3. 更新在线时间、运动状态、诊断和协议事务状态。
4. 处理低频发现/配置事务的状态机。
5. 按 P0/P1/P2 优先级向三路硬件 TX FIFO 泵送帧。

该节拍是服务频率，不是 1 kHz 控制频率。任何单次工作都必须有上限，不能在其中
等待 ROS、Agent、设备响应或 W25Q64。

### 3.3 2 ms / 500 Hz 控制边界

1. 复制 `command_snapshot_mailbox` 中最新的完整命令快照。
2. 校验 `sequence`、时间、ID、数值、重复项、策略和设备生命周期。
3. 快照中缺席的已受控电机执行软停，不沿用上一周期目标。
4. 超过 30 ms 没有新快照时进入软停；超过 100 ms 或 micro-ROS 会话断开时发送
   协议级停机/失能并清除运动授权。
5. 只有 `ACTIVE` 且通过安全检查的电机才由适配器生成 MIT 控制帧，写入该总线的
   P1 latest-wins 槽；实际发送由 1 ms 服务完成。

恢复必须重新收到有效策略、显式 Enable 和新的完整运动快照，不能自动复用旧命令。

## 4. 运行时注册表和生命周期

注册表是编译期有界的，容量至少覆盖 64 台设备。表项只保存运行时事实和引用：

| 数据组 | 内容 |
|---|---|
| 定位 | `motor_id`、`bus_index`、最近接收时间 |
| 身份 | 协议、厂家型号、版本/序列号（协议提供时） |
| 能力 | 支持模式、编码器/单位换算、设备限值和限位能力 |
| 控制 | 当前策略、Enable、命令序列、目标和 freshness |
| 状态 | 位置、速度、力矩、电流、电压、温度、模式、故障 |
| 诊断 | RX/TX 统计、协议错误、事务状态和最近失败原因 |

生命周期保持简单：

```text
ABSENT → DISCOVERED → IDENTIFYING → READY_DISABLED → ACTIVE
                                      │       │
                                      └───────┴→ SAFE_STOP / FAULT / CONFIG_CONFLICT
                                                        │
                                                        └→ OFFLINE → DISCOVERED
```

只有 `ACTIVE` 允许发送运动目标；所有其他状态保持禁能或发送安全动作。

## 5. 型号和协议适配器

### 5.1 型号 Profile

Profile 是编译期型号目录，不是每台电机的安装表。至少包含协议类型、编码器和单位
换算、减速比、额定/峰值参数、默认 MIT 参数及限位能力。运行时由设备身份选择；
上层保留对应副本用于关节配置和校验。

规格书已确认的型号基线：

| 型号 | 主要参数 | 运行方式 |
|---|---|---|
| CERB R48-101 | `101:1`、30 RPM、额定/峰值 `5/11 Nm`、48 V、21 bit 编码器 | CAN，支持驱动器侧限位配置 |
| CERB R58-101 | `101:1`、30 RPM、额定/峰值 `20/45 Nm`、48 V、21 bit 编码器 | CAN，支持驱动器侧限位配置 |
| Vaxor 25 mm 系列 | 12~18 V、绝对编码器；规格书明确给出 30/50 速比参数 | CAN-FD，上电默认 MIT，无硬件限位 |

Vaxor 系列名中的 80 速比当前没有完整参数，不能用 30/50 档外推；补齐规格前不
加入可用于控制的 Profile。

### 5.2 适配器边界

| 能力 | Vaxor | CERB |
|---|---|---|
| 身份 | 从每 20 ms 自主状态识别型号 | 通过反馈/管理读取识别 |
| 默认控制 | 标准 MIT 单电机帧：`0x501 + 4*N`，12 字节 | MIT 单电机帧：`0x110 \| Dev_ID`，9 字节 |
| 反馈 | 自主状态；MIT 命令也可有响应 | 默认 MIT 命令反馈；SYNC 用于发现/探测 |
| 多电机帧 | 不使用 | `0x200` 仅在明确的非 MIT 模式使用 |
| 限位 | 固件软件限位 | 驱动器侧配置，MCU 负责事务和核验 |

通用运行时只处理“身份、能力、状态、控制意图、原始 CAN 帧”。新增协议只增加
适配器，不修改 `motor_rt_task`、mailbox 或总线调度器。

### 6.1 高频接口

上层控制器只使用 `ros2_control` 官方 `position`、`velocity`、`effort` command
interfaces；`sensor_msgs/msg/JointState` 只用于上层状态发布，不作为控制命令。

| 接口 | 必要字段/语义 | 方向 |
|---|---|---|
| `MotorCommandArray` | 同步时间、`uint32 sequence`、`uint8 count`、最多 64 项；每项 `uint16 motor_id` 和 `float32 position/velocity/effort` | 上层 → MCU |
| `MotorMotionStateArray` | 同步时间、最多 64 项；每项 `motor_id`、位置 `rad`、速度 `rad/s`、力矩 `N·m`、`state_age_ms` | MCU → 上层 |
| `MotorStatusArray` | `motor_id`、温度、电流、电压、驱动模式、统一故障码、厂家故障码、保护/限位标志、`online`、生命周期、`state_age_ms` | MCU → 上层 |
| `MotorTopology` / `MotorEvent` | 总线、协议、型号、能力、上线/离线/冲突等低频信息 | MCU → 上层 |

高频自定义消息中的物理量使用 `float32`；上层转换为标准 `JointState` 的 `float64`。
状态缺失的浮点量使用 `NaN`，逻辑 `motor_id` 使用 `uint16`，原始 CAN ID 使用
独立的 `uint32`。状态消息不携带 `joint_name`。

`protection_flags` 和 `limit_flags` 只使用集中定义的位标志；位编号放在消息/代码
常量的单一位置，不在业务模块中散落。当前统一单位为：电流 `A`、电压 `V`、温度
`°C`、限位数值 `rad`。

### 6.2 低频接口

| 接口 | 内容 | 规则 |
|---|---|---|
| `MotorPolicy` | Enable、MIT `Kp/Kd`、前馈、软件限幅、安全授权 | 运行时策略，不进入 100 Hz 命令 |
| `MotorConfig` | 模式切换、CERB 限位及其他设备配置 | 请求/结果事务，不刷新运动 freshness |

`MotorConfig` 的最小规则：

- 每个请求带 `request_id`；同一 `motor_id` 同时只允许一个未完成事务。
- 有未完成事务时新请求立即返回 `BUSY`，不排队、不覆盖。
- MCU 先校验请求和型号能力，再由协议适配器执行设备操作。
- 需要设备确认的参数必须读回一致后才返回 `OK`。
- 超时按协议阶段处理，可重试步骤最多自动重试 2 次；写入结果不明确时先读回，
  不盲目重复写入。
- 最终不能确认时不恢复运动授权。

统一结果码保持最小集合：

| 码 | 含义 |
|---|---|
| `OK` | 操作完成且已验证 |
| `BUSY` | 同一电机已有未完成事务 |
| `INVALID` | 消息或参数非法 |
| `UNSUPPORTED` | 当前型号/协议不支持 |
| `DEVICE_ERROR` | 驱动器拒绝或协议执行错误，细节看厂家码 |
| `TIMEOUT` | 阶段超时且重试耗尽 |
| `UNCONFIRMED` | 写入/读回结果无法确认或不一致 |

### 6.3 固件记录为设备参数的权威（2026-09-21 反转 09-17 口径）

CERB 的位置限位（`0x607D:01/:02`）、最大转速（`0x6080`）、峰值电流（`0x2538`）
存在驱动器里，但**固件内部维护的那份记录是权威**：驱动板参数要与固件对齐，初始化
语义的来源是固件而不是设备。本节 09-17 的原文（"设备参数以驱动板为准、固件记录只作
比对基准"）方向相反，**已由 维护者 于 2026-09-21 明确反转**——那个方向会让"设备里被
外部工具改过的脏值"成为通过标准。

- **上电/重连比对**：绑定完成后内核自动发一次 `REFRESH_PARAMS`（4 个快速 SDO
  upload），把回读值与本机记录**逐槽位比设备端原值**（cnt / 电机端 RPM /
  电机端 mA）。比关节侧 SI 值是不行的：两端都过同一套 `Kt × 减速比 × 效率`
  换算，系数配错时两边一起错、比对恒通过。
- **一致** → 初始化通过。
- **初始化未完成一律不可使能**：`PENDING`（回读未收尾）/`MISMATCH`（与记录
  不一致）/`UNVERIFIED`（回读失败）/`NO_RECORD`（本机无该台记录）四种结论下进
  `CONFIG_CONFLICT`、冻结逐电机授权、拒绝 `SET_ENABLE`、不出运动帧；`param_bridge`
  报 `system_status.last_error=40`（不一致）/`41`（未核对）/`42`（无记录）+
  `last_error_motor`（话题名勘误：参数服务器 2026-09-21 退役）。
  恢复路径是人工：从 `param_set` 写回该台参数（写事务成功即更新记录，随即重判），
  或重连后再读一次。
  不引入"固件侧出厂默认值"：首次上电（W25 无该台记录）固件侧显示「无记录」、判
  未初始化，走人工核对；写下去之后记录即成立（维护者 2026-09-21 定）。
- **运行中回读发现不一致 → 软停**（P0 MIT 阻尼帧、保留使能，TBD-SAFETY-01
  口径），不硬失能；静止态没有要停的东西，直接锁存结论。
- **自动回读失败先退避重试**（≤3 次、间隔 500ms）：SDO upload 是纯只读事务，
  对设备无副作用，多问几次不改变任何状态；用尽才定论 `UNVERIFIED`，避免一次
  总线抖动在"初始化未完成不可使能"的口径下把该台卡死。重试期间维持 PENDING。
- **记录里没有的槽位不参与比对**（刚烧录、Flash 为空的电机不该整体卡住）；
  **唯一例外是方向槽（`0x2541`）**：它易失、设备每次上电回 0，"设备读到 0"零信息量，
  故记录缺这一槽 = 方向未知 = 未初始化（`motor_control_config.c:112-124`）。
  VAXOR 没有设备对象，恒不参与（`dev_init=NA`）。
- **写 ≠ 保存（2026-09-21 分离，2026-09-22 收紧完成判据）**：设备侧写事务读回
  核验通过后，内核用该事务实际编码出的原值同步固件记录并置 `record_dirty`，**写
  事务本身只改设备 RAM 与记录、不落盘**；`0x2539` 已挪进独立的 `SAVE_DEVICE_FLASH`
  保存事务，由 `system_command` 的 `COMMAND_SAVE` 触发（勘误：原 `system.save`），
  按脏槽位选保存码（1/2/4，不写无关对象）。本轮收紧为：每台设备保存请求必须先
  返回 `CONFIG_RESULT=OK`，之后才请求 W25；W25 的目标槽擦除、整 blob 写入、分页读回
  校验和活动槽切换全部完成后，才把整笔 SAVE 判为成功。任一设备结果非 OK 时不启动
  W25。控制边界里原先"写成功后 500 ms 去抖自动落盘"已删——记录不落盘就断电，下次
  上电判不一致，那时该台未初始化，是设计使然。CERB 的 `0x2539` 阶段本身无设备应用
  层应答，因此 `CONFIG_RESULT=OK` 不是物理 flash 耐久性的独立证明，仍待掉电台架。
- **持久化格式**：W25 blob v2（32B 头 + 64×48B 记录，含 4 个 `device_raw`），
  v1 由 `param_store_blob_migrate_v1()` 就地升级。

> ⚠️ **本节 2026-09-21 的新口径尚未上板验证**：`NO_RECORD`/`last_error=42`、写/保存
> 分离、`0x2539` 独立保存事务与 `device_param_report` 话题均只经 host 测试与静态审查，
> 真机台架项见根 `README.md` 的开放项一节（**未运行**）。

### 6.4 参数面的对外单位（2026-09-17 定；2026-09-20 改位置/速度）

> **勘误（2026-09-21）**：承载这套单位的 `rclc` 参数服务器已整体退役，参数面改为
> 下行 `micro_ros_do/param_set`（`ParamSetArray`）/ `system_command`、上行
> `micro_ros_up/system_status`。**本节结论一字未改**：单位口径、`param_units.h`
> 的换算位置、力矩列用 A 的理由全部照旧迁移——`param_bridge` 仍是唯一换算边界，
> 写入侧的 A→SI 换算仍只在 `submit_single_limit` 一处。唯一命名变化：参数名
> `m<id>.<field>` → `param_set` 的 `motor_id` + `field`（**设备槽序**，见 §6.12 勘误）。

参数面对外与内核 SI **同单位**，只有力矩列是工程单位：

| 参数 | 对外单位 | 内核 SI | 换算 |
|---|---|---|---|
| `pos_min` / `pos_max` | **rad** | rad | 直通 |
| `vel_limit` | **rad/s** | rad/s | 直通 |
| `torque_limit` | **安培** | N·m | ÷限值系数（见 §6.6） |

- **2026-09-20 改动**：位置/速度此前对外是**度、度/秒**（原 §6.4），现改回 rad、rad/s。
  理由是参数与状态同屏：`motion_states`、URDF、曲线都是 rad，参数树却是度，操作员
  要在同一块界面上换算两套角度，而换算常量还得多带一个 π 到前端。全链路一套单位
  也让参数值可以直接和状态值比对（例如限位 ±3.14 对位置 0.03）。力矩列不变。
- 力矩换算只在 `param_bridge` 边界做一次（`lib/param_store/include/param_units.h`，
  host 可测）；位置/速度是直通，边界不再有角度换算。前端与内核都不各自换算，
  避免重复缩放。
- **力矩列用 A 而不是 N·m**：设备侧的权威对象是 `0x2538`（厂家手册：「电机最大
  电流参数」，mA，且「最大电流建议用默认（与电机峰值电流保持）」），把它折成
  N·m 要过一次系数，而该系数本身存在未决争议（§6.6 的 TBD-PROFILE-02）。用 A
  显示的正是设备里存的值。
- 系数缺失（未绑定型号）时力矩列不换算（NaN），写方向直接本地拒绝——宁可显示
  不了，也不拿瞎猜的系数下发。

### 6.5 配置事务按总线一问一答（2026-09-17）

厂家的 CANopen SDO 是**严格请求-应答**（说明书示例全是一问一答）。内核原先允许
各表项的事务并行步进，同一总线上可能同时挂着多条未决请求。台架实测（4 台 CERB、
SLCAN 链路）出现"回读一直超时"：设备按序处理请求，迟到的应答与本阶段索引不符
→ 判 RETRY → 重发 → 设备更慢；log 上表现为同一台两条请求间隔约 940ms 的超时-
重发循环。

- 内核在发送阶段前检查 `bus_stage_in_flight()`：**同一总线任一时刻至多一个
  "已发未答"阶段**。无应答阶段（VAXOR 本地策略）不受影响；不同总线互不阻塞。
- CERB 阶段超时 20ms → 30ms。
- 上位机判断回读收尾用只读量 `refresh_seq`（每次 param 桥发起的回读收尾 +1，
  无论成败）——只看 `last_error(_motor)` 分不清"这一轮"与上一轮残留。
  *（2026-09-21 勘误：原为 `system.refresh_seq` 参数，现为
  `micro_ros_up/system_status` 的 `refresh_seq`；判据理由完全不变，仍是"序号只增
  不减、每次收尾无论成败都 +1"。）*
- 代价：多台并行收敛变慢（N 台 × 4 阶段串行）。配置事务本来低频，可接受。

### 6.6 固定硬件参数表与外部写入钳制（2026-09-17）

`motor_control_profile.c` 的编译期型号目录**就是固件的固定硬件参数表**，外部写入
一律不得超过它。规格书（`docs/CE-RB-R58-101-Lite-CO-I-参数规格.pdf`、
`docs/CE-RB-R48-101-Lite-CO-I-参数规格.pdf`）的电气列原先漏进表里，已补齐：

| 型号 | 减速比 | 额定/峰值转矩 | 额定/峰值电流 | 扭矩常数 | 输出转速 |
|---|---|---|---|---|---|
| CE-RB-R58-101 | 101:1 | 20 / 45 N·m | 3.5 / **10.8 A** | 0.086 N·m/A | 30 RPM |
| CE-RB-R48-101 | 101:1 | 5 / 11 N·m | 1.3 / **3.2 A** | 0.077 N·m/A | 30 RPM |

外部写入按维度取更严者钳制：

- **扭矩/电流**：`min(请求, 峰值扭矩, 峰值电流 × 限值系数)`；
- **速度**：≤ 额定转速（π rad/s 关节侧 = 3030 RPM 电机侧）；
- **位置**：≤ MIT 量化范围 `mit_position_limit_rad`（±π，与设备 0x607D 的
  ±32768 cnt 同域）。

**限值对象（0x2538）的换算系数改用规格书峰值对** `peak_torque / peak_current`
（R58 = 4.167、R48 = 3.4375 N·m/A），不再是反馈链的 `Kt×减速比×效率`
（8.686/7.777）。理由：写"峰值扭矩"就应当正好写出"峰值电流"——规格书两端都写着，
用它换算才让"不得超过硬件参数表"在扭矩与电流两个维度同时成立（先前写峰值扭矩
只落 5181 mA，是规格书峰值电流的一半：过保守，且与规格书自身矛盾）。
**反馈**（Iq → 实测扭矩估计）仍走 Kt 链——一个是限值映射，一个是物理估计。

**设备侧写事务以"写 FLASH"收尾**：厂家手册明确「0x607D 设置完成后需要保存
Flash」「0x2539 将写入的 PI 和最大电流保存 FLASH」——**驱动器里的限值默认只落在
RAM**，掉电回出厂值。写事务因此追加末阶段 0x2539，**无应答、不重试**（写 flash
期间驱动器的控制循环会被阻塞，等 ack 只会把总线一起拖住）；是否真落盘由"下次
上电的设备参数比对"检出——不一致即判未初始化，这正是该机制的用途。

保存码取自《CERB巨蟹智能-CANopen-V0.9字典表》（`docs/` 内）0x2539「Flash保存
参数代码」：**1 = 断电保存设置的电机参数**（0x2538 最大电流、0x6080 最大转速、
PI 等）、**2 = 设置电机正限位**（0x607D:02）、**4 = 设置电机负限位**（0x607D:01）。
故速度/电流事务发 1，位置限位事务发两条（先 4 后 2）。**只发 1 不足以保存限位**
——这是首版实现的错误，已按字典改正。

字典同时给出位置限位量程：`0x607D:01/:02` 均为 **-32767 ~ 32768 cnt**（默认
-32767 / 32768）。`-π rad` 折算正是 **-32768**，比下限低 1 cnt，故
`cerb_rad_to_limit_cnt` 末尾按字典范围钳制。字典另给 `0x2538`「电机峰值电流」
（mA，0~32768，与"限值换算用峰值对"一致）与 `0x6077`「力矩传感器当前值」
（RO，0.01 N·m）——后者是 TBD-PROFILE-02 的现成判别手段。

**未决（TBD-PROFILE-02）**：规格书自身有三套互不一致的口径：
① 自报 Kt 0.086/0.077；② 额定/峰值两点隐含关节侧 N·m/A 4.167~5.714（R58）、
3.438~3.846（R48），隐含效率随负载从 0.66 掉到 0.48，单一常数无法同时命中；
③ 反电动势常数 5.3/4.7 V/krpm 折算 Kt ≈ 0.0506/0.0449，与自报 Kt 差 1.70×。
限值口径已不依赖它（§ 本节的峰值对），**但反馈扭矩估计仍依赖**：若真实 N·m/A
只有名义值的一半，上层看到的力矩会比实际大一倍。判别实验（**字典给了现成手段**）：
`0x6077` 力矩传感器（RO，0.01 N·m）与 `0x6078` 电流（RO，mA）同时可读——静止
重力载荷下 `Kt_eff = (0x6077×0.01) / (0x6078/1000 × gear)`，不必外接扭矩传感器；
或 MIT 下扫几个前馈点做最小二乘。

### 6.7 设零点（2026-09-17）

设备对象 **0x2531「设置电机输出端零位」**（字典表 RW，默认 0，范围 0~2；说明
「写入零位是电机需要在去使能的状态，写 1 时设置零位」）。

- 事务形态：**单阶段写 0x2531=1**，等 SDO 写应答（0x60）即完成，**不读回**——
  它是命令式对象，读回值的语义未定义，读回核验只会制造假失败。
- 门禁：与设备侧限位同源，复用 `device_limit_write_allowed`（ACTIVE/SAFE_STOP
  一律 `INVALID` 拒绝，**不隐式失能**）。厂家手册明确要求失能态设置。
- 不动任何本机状态：零点不是本机记录的参数，**不更新设备影子、不更新 W25 记录**。
- 上位机入口：`micro_ros_do/system_command` 的 `COMMAND_SET_ZERO` + `motor_id`
  （触发式，仿 refresh）+ `micro_ros_up/system_status` 的 `set_zero_seq` 完成序号
  （据此确认收尾，判据理由同 §6.5）。*（2026-09-21 勘误：原为参数
  `system.set_zero = <电机 id>` / `system.set_zero_seq`。）*
- ⚠️ **零点改变 = 设备里 0x607D 限位的物理位置随之改变**：操作者必须重新确认
  限位与机械行程。本机记录里的限位原值（cnt）不变，故上电比对不会误报。
- **持久化已实测（TBD-ZERO-01 结案，2026-09-17 台架）**：字典 0x2539 的保存码只列
  1=电机参数 / 2=正限位 / 4=负限位，没有"零位"项；实测**设零后给驱动器断电重上电，
  零位保持** → `0x2531` 写入即由驱动器自行落盘，**无需额外发保存码**。故设零事务
  保持单阶段，不追 0x2539（多发一条错的码既无效又要承担写 flash 阻塞控制循环的代价）。

### 6.8 下行多点轨迹通道（2026-09-18）

**问题**：100Hz 完整快照给的是"当前设定点"，轨迹/示教回放只能由上层逐点插值，
运动质量受主机抖动影响，下行带宽也是随点数线性增长。

**决定**：新增 `MotorTrajectory`（扁平、按时间升序的 (时间, 电机) 路点表 +
独立的 `target_ids` 受控集合），MCU 在 2ms/500Hz 控制边界按整条拼接时间线插值（见下条）。

- **扁平而非二级嵌套**：rosidl 的二级有界序列要为每个外层元素各自预分配内层
  buffer，静态初始化复杂且容量按 N×K 预留；扁平表单层一处预分配、按内容占用。
- **整数毫秒的 `time_from_start_ms`**（相对起点），不用 ROS 时间：控制边界就是
  5ms，亚毫秒无意义；绝对时间会把 MCU 拖进 epoch/NTP 依赖（ARD §12.1）。
- **速度取解析导数，不直通路点字段**：MIT 律是 `τ=Kp·Δp+Kd·Δv+τ_ff`，上层常把
  `velocity` 填 0，直通会让 Kd 朝 0 速刹车。字段保留作诊断。
- **插值：非均匀单调三次 Hermite（2026-09-22 维护者 确认）**：位置按相邻路点的
  不等时间间隔求 Fritsch–Carlson 切矢，段内使用三次 Hermite，速度由曲线解析求导，
  不读取 `point.velocity` 作为执行速度。局部极值切矢为 0，并限幅到相邻割线的
  `3×min(|Δ|)`，保持单调且避免超调；内部路点的切矢由左右时间间隔共同计算，
  因此分段拼接后的边界速度连续，首尾端点保持零速。
- **分段组装**：同一 `trajectory_id` 的可靠分段携带 `segment_index`（0-based）和
  `segment_count`，固件要求按序到达，在固定 assembly 缓冲中拼接，拼接后总路点数
  不超过 256。分段未收齐时当前轨迹继续运行；最后一段完成且整条校验通过后才
  原子发布到 mailbox。时间采用整条轨迹共同的 `time_from_start_ms`，不按段重置。
  相邻分段在同一电机同一时间的完全重复点合并，位置、速度或前馈冲突则整组拒收。
  不引入动态内存；拼接缓冲增加的 RAM 需以目标链接图重新确认。
- **2026-09-21 线性方案**：曾短暂作为实现决策，原因和测试记录保留在变更记录中；
  已被 2026-09-22 维护者 决策取代，不得作为当前行为依据。
- **实现备注（2026-09-22）**：历史记录中“解注释三处即可恢复线性”的回滚提示不再
  适用于当前树；死代码注释已删除，若要实验性恢复必须从历史提交或独立补丁取回，
  不应在当前源码中寻找可切换开关。
- **归属仲裁（关键）**：轨迹声明集合内的电机由轨迹**独占**，快照对它们既不下发
  也不软停；集合外仍受 §13.1「缺席即软停」。**快照不是解除路径**——任何 100Hz
  周期发布者都会立刻打死轨迹。解除只有三条：被新轨迹替换（移出者立即软停）、
  空轨迹取消、会话断链。
- **归属是纯派生的**：`(trajectory_active, target_ids, motor_id)`，不落字段。
  故障/离线/冲突/设备参数未核对各自把表项带离可动生命周期，自动脱离轨迹，
  无需在那几条路径里额外清理归属。
- **freshness 按通道分割**（对 ARD §13.2 的范围限定）：30/100ms 级联只作用于
  快照通道的电机，全局授权电平不动（它由会话电平每边界派生，与快照流是否活跃
  无关）。**无活动轨迹时走原来的全局 `revoke_motion`，行为逐字节不变。**
- **播完保持末点**：机构无抱闸，软停会掉臂。上层按自己发出的末点时刻判断结束。

**代价**：分段 assembly 增加一个固定 256 点轨迹缓冲，禁止动态内存。2026-09-22
目标链接测得 `.data + .bss = 310,220 B`，其中落在 320 KiB RAM_D1，约 **94.7%**；
PlatformIO 全 RAM 口径为 53.7%，Flash 为 20.5%。保存请求跟踪表又增加 256 B，历史 31 KB、196,724 B 和 206,324 B
不能作为当前基线。轨迹校验是 O(路点×电机) 且在临界区内，分段发布是低频动作——
最坏耗时列为 TBD-RT-02；RAM_D1 余量列为 P1 资源风险，后续不得继续增加静态大对象。

### 6.9 故障清除入口（2026-09-18）

**问题**：内核原本**没有**任何清故障 API；厂家故障只能等设备自报
`fault_active==false`，DEV_PARAM 只能靠重写参数或重连。操作者在页面上"按了没反应"。

**决定**：`micro_ros_do/system_command` 的 `COMMAND_CLEAR_FAULT` + `motor_id`（脉冲）+
`micro_ros_up/system_status` 的 `clear_fault_seq`。**不用服务**——判据是本条动作
与 `REFRESH`/`SET_ZERO` 同类（"写 = 电机 id、轮询序号判完成"的命令/应答协议），
不是可被同时多方调用的请求/响应接口。

> **⚠️ 本节是"参数面为什么存在"的最后一处正面论证，2026-09-21 在此结案。**
> 本节 09-18 原文给出的两条理由都要更正：
> 1. ~~"逐电机动作的既有台架已验证通道就是参数（`m<id>.enable`、`system.set_zero`、
>    `system.refresh`）"~~ —— 这是**当时的事实**，不是理由。`m<id>.enable` 今天已
>    改由 `motor_policy` 话题承载（§6.11），同一批动作现在分散在两条话题上，
>    参数面上的"统一通道"这个好处从来没有兑现过。
> 2. ~~"MCU 侧的 service 额度（`MAX_SERVICES=5`）已被 rclc 参数服务器占满，加服务
>    要重建 libmicroros"~~ —— 这是**沉没成本**，不是设计理由。它把"已经占了额度"
>    当作"该继续占"的依据。事实是那 5 个槽位从来没用过（`system_status` 的四个
>    完成序号已覆盖全部命令回执需求），退役后成为纯余量。
>
> **结论**：全仓库没有一句"为什么用参数服务器而不是话题"。它是一次未加论证的
> 初始选择，被后续三轮决策（§6.4 / §6.9 / §6.12）当作既成事实继续引用，代价是
> 每台电机 6 个槽位 × 328 B 的常驻 DTCM 堆。2026-09-21 维护者 裁定整体退役为话题
> （`param_set` / `system_command` / `system_status`）。**教训**：引用前一轮的
> 选型作为本轮的理由之前，先问那个选型本身有没有理由。

内核按**成因**三分支（不是按生命周期——DEV_PARAM 与身份冲突都在 `CONFIG_CONFLICT`）：

| 成因 | 动作 |
|---|---|
| 身份冲突锁存 | **拒绝**（ARD §9.3 刻意不可解除，只能整机重启） |
| DEV_PARAM | 改走一次 `REFRESH_PARAMS`，重跑回读与比对；真不一致仍保持锁存（不伪造一致） |
| 厂家故障 | 发清错帧（CERB MIT 控制字 **bit5**）；Vaxor 无此位 → `UNSUPPORTED` |

**仅非运动态受理**（与设备侧限位写同口径：安全边界不在运动中变动）；清错帧
**不请求使能**（bit7=0，避免把"清错"变成隐式使能）。清完仍须显式
`SET_ENABLE(true)` + 新证据（ARD §36）。

**代价**：系统参数 8 → 10，`kMaxMotors` 由 17 降到 **16**。这是容量回退，已在
README 与验证计划记录；可读完成序号不能省（只看 `last_error` 会把上一轮残留
当成这一轮的结果）。

*（2026-09-21 勘误：`kMaxMotors` 这个容量本身是参数服务器的产物，随退役一起消失
——`system_status` 的四个序号是固定字段，与电机数无关。上面那句"容量回退"的代价
至此归零；但"可读完成序号不能省"这条结论**反向加强了**：没有服务器之后，
`system_status` 是**唯一**的完成判据来源。）*

### 6.10 容量常量按 48 台上限校准（2026-09-18）

**背景**：设计点定为 **48 台上限、实际部署约 40 台**。内核与消息的容量常量**保持 64
不动**——AXI 还剩 127.9 KB，不是稀缺资源；砍到 48 只省约 4.6 KB 却要改掉每一处
static_assert 与消息数组边界。稀缺的是 DTCM（参数槽常驻堆），所以只校准参数面
和三个"48 台时正好顶到边界"的常量。

| 常量 | 原值 → 新值 | 理由 |
|---|---|---|
| `MOTOR_CONTROL_MAX_EVENTS` | 64 → **128** | 48 台同时上电会在一个 10 ms 桥轮询里挤进最多 48 条 DISCOVERED（每台首帧即出事件）；PROFILE_BOUND/READY 走身份读取、被 `config_step` 限速在 1 台/ms，是摊开的。原值 64 对并发发现没有余量。 |
| `MOTOR_CONTROL_MAX_TX_PENDING` | 96 → **160** | 一批未搬走的 P1（48 帧）与 30 ms 软停级联的 P0（48 帧）同拍 = 96，正好顶到上限。 |
| `CAN_TX_P0_CAPACITY` | 16 → **32** | 48 台分摊到 3 条总线是 16 台/总线，正好等于容量。 |

**代价**：`.data`+`.bss` 从 196,724 B 增到 **206,324 B**（+9,600 B），RAM_D1 占用率
**63.0%**；Flash 232,656 B（22.2%）。

**顺带修掉两条会静默失效的 host 用例**：它们写死数字去撞容量边界，常量一变就失去
覆盖——事件环用例靠喂 1..136 号设备首帧灌环，但厂家 node 空间只有 1..127（CAN 节点
上限，不是产品上限）；TX 丢弃用例写死 120 次迭代，容量提到 160 就撞不满。已改成按
容量常量推导 + 用不受设备数限制的事件源（整快照拒绝）。

**未做：轨迹缓冲去重。** 轨迹缓冲在 `.bss`（AXI）上，而 AXI 不紧张；删掉它要么让
ROS 回调在关中断下填 5 KB，要么把轨迹 mailbox 的双缓冲降成单缓冲——用削弱并发契约
去换不紧张的资源，不划算。

### 6.11 逐电机策略走独立 mailbox（2026-09-18）

**问题**：`enable`/`kp`/`kd` 是动态量，ARD §15.4/§19.4 禁止它们进 100Hz 命令
快照；而参数树在 48 台上限下装不下 7 项/台（见 §6.12）。它们需要一条自己的
下行通道。

**先试过、被否掉的方案**：复用内核的 config FIFO（每条策略消息按台拆成一条
config 请求）。**走不通**：config 队列深 16，而一条策略消息最多 64 台，48 台
会有 32 台被丢弃计数，策略变成部分生效。config FIFO 是给「低频、逐台、带设备
事务」的请求用的，策略是「批量、本地立即生效」——塞进同一条队列是类别错误。

**决定**：新增 `control_policy_mailbox`（与 command/trajectory 同构、双缓冲
latest-wins、稀疏语义）。内核保留 `SET_POLICY {enable, kp, kd, generation}`
作为**单台入口**，批量入口 `motor_control_apply_policy` 逐台复用同一套落地
逻辑——两个入口、一份实现，不是两条路径。

**代数门实现为一处判定**（比原设想简单）：规则是「`policy_enable` 当前为 false
时，`enabled=true` 要求 `generation` 严格前进（初值 0，首次武装至少为 1）」。
FAULT/OFFLINE/CONFIG_CONFLICT/DEV_PARAM 四条冻结路径本来就都清 `policy_enable`，
所以**它们一处都不用改**。它挡不住「每次都递增代数的周期发布者」——那与人工
逐次授权在行为上不可区分；ARD §36 的「显式」在机制层面到此为止。

**已知的代价**：逐台成功也会各出一条 CONFIG_RESULT 事件，故策略是**低频接口**
——高频发布会把事件环灌满（丢弃数在 diagnostics 话题可见）。

### 6.12 参数面按静态/动态重新划界（2026-09-18；**2026-09-21 整体作废**）

> **⚠️ 勘误（2026-09-21）：本节的全部槽位核算已随参数服务器退役作废。**
> `PARAM_BRIDGE_MAX_PARAMS`、`PARAM_MOTOR_FIELD_COUNT`、`kMaxMotors`、
> "参数槽 56.6 KB DTCM 堆"这些量与算式**都不再存在**——参数面现在占 0 字节常驻堆
> （三条话题的订阅/发布控件与消息体是静态 `.bss`，与电机数无关）。
> 本节保留作**历史推导**：它是"为什么参数服务器在 48 台设计下不成立"的完整论证，
> 也是 §6.9 结论里"三轮决策把未加论证的选型当既成事实"的第二轮。
> 下文原文不再逐行改写。**退役决定**见 §6.9 的结论块与变更记录末行。

**问题**：rclc 参数服务器每槽约 269 B（反汇编实测 `sizeof(Parameter)=112` +
`sizeof(ParameterDescriptor)=68` + 50 B 名 + 12 B names 数组），且 init 时**一次
性全部分配**，与注册了几台无关。7 项/台在 48 台上限下要 346 槽 ≈ 89 KB，而参数
槽所在的 DTCM 堆池只有约 116 KiB（FreeRTOS 任务栈另占 44.5 KiB）。

**决定**：参数树只放**静态量**（`pos_min`/`pos_max`/`vel_limit`/`torque_limit`
四项/台 + `system.*`），动态量 enable/kp/kd 移到 `/micro_ros_do/motor_policy`（§6.11）。
`PARAM_BRIDGE_MAX_PARAMS` 128 → 208，覆盖 48 台上限（48×4 + 10 = 202）。

**`param_field_t` 保持 7 项不动**：它是 Flash blob 的 `present` 位图契约与记录
布局；退役的三项只是不再被注册，布局不变、**无需迁移**。参数桥的槽位算式分母
单独用 `PARAM_MOTOR_FIELD_COUNT = 4`。

**代价**：参数槽从 35.0 KB 涨到 56.6 KB（+21 KB DTCM 堆），堆池余量估算约 26 KB，
**无实测高水位**——这是本计划最大的未确认项，验收必须读 `system.heap_free` 最低位。

## 7. FDCAN 缓冲和发送调度

### 7.1 接收

每条总线一个独立的静态 RX 环，初始深度为 64 帧；帧元素至少包含：

```text
can_id, is_fd, is_brs, dlc, data[64], rx_tick, bus_index
```

FDCAN ISR 只完成取硬件 FIFO、加时间戳、写环和计数；满时丢弃并累计溢出。协议
解码、拓扑更新和状态更新全部由 `motor_rt_task` 完成。CAN 调试桥删除，任何调试
信息只能读取状态副本、拓扑事件和统计计数。

### 7.2 发送

每条总线一个独立调度器：

| 优先级 | 内容 | 规则 |
|---|---|---|
| P0 | 停机、失能、急停、安全帧 | 最高优先级，按电机去重 |
| P1 | MIT 控制（**控制边界 2 ms/500 Hz**，2026-09-23 起） | 每台电机一个 latest-wins 槽，不积压旧目标 |
| P2 | SYNC、身份/能力读取、配置事务 | 有界管理队列，不能挤占 P0/P1 |

默认 MIT 不使用聚合 CAN 帧：同一总线有多少台活动电机，就生成多少条单电机 MIT
帧；CERB 超过 8 台也不因此切换到 `0x200`。`0x200` 只在明确的非 MIT 模式下由
CERB 适配器启用，并按每组最多 8 台拆分。

CAN-FD 侧的正常性由三件事保证：协议适配器独立组帧、P1 只保留最新目标、1 ms
调度器持续泵送硬件 FIFO。最终仍需在最大电机数和最坏反馈流量下实测总线负载、RX
溢出、TX 延迟和控制抖动，测试不通过时只调整容量/配额，不改变 ROS 与 CAN 边界。

## 9. DMA、MPU、WS2812、BMI088 和 W25Q64

- FDCAN 正常收发不依赖 DMA；先用中断 + 静态环实现可测量的路径。
- WS2812 属于低优先级显示；若阻塞发送影响 FDCAN 延迟，改为 SPI TX DMA。DMA
  缓冲放在 MPU/cache 策略明确的非缓存区，或在收发前后做 cache maintenance。
- BMI088 不进入电机实时任务；按现有独立任务运行，只有测量证明需要时再引入 DMA。
- W25Q64 不保存电机实时控制状态、上层关节映射或型号 Profile；由单独
  `storage_task` 写入低频事件/故障日志，禁止阻塞 1 ms/10 ms 路径。
- MPU 配置服务于 DMA 缓冲、外设区和任务隔离，不把 MPU 规则扩散到协议业务代码。

## 10. 实施顺序

1. 固化消息包、枚举、Profile 数据结构和静态容量常量。
2. 重构 `lib/fdcan`：三路 RX 环、ISR 所有权、TX 调度器和统计。

## 12. CERB 设备对象事实与待厂商项

原 `docs/plans/active/cerb-vendor-questions.md`（2026-09-19 立）并入本节后删除。

### 已结案（无需再问厂商）

| 项 | 结论 |
|---|---|
| `0x2650:00` 读子索引 | 是 **`0x00`**；`:01`/`:02` 回 ABORT `0x06090011`（子索引不存在）。读 `40 50 26 00 00 …` → `43 50 26 00 0x …`；`23 50 26 00 00 …` = 开启保护、`… 01 …` = 关闭。台架四台上电初值均为 `1`（关闭） |
| 位置限位子索引方向 | 手册「读取正/负限位」两行与设置行相反，属**手册笔误**。`:01` = 下限（-32768）、`:02` = 上限（+32768）；固件 `kStagesPositionLimits`/`kStagesRefresh` 方向正确，反向修改会真的把设备限位写反 |
| `0x2541`（电机方向） | 写 `23 41 25 00 0X 00 00 00`（0 = CW、1 = CCW），读 `40 41 25 00 00 00 00 00`，取值 0/1。**掉电不保存**（与 `0x2650:00` 同形）⇒ 固件在上电归一里按 W25 记录写回。写事务 = 写 + 读回核验，仅未运动时受理 |
| `0x2650` 的保存码 | **不存在也不需要**。官方 §4.11 的码 `1` =「PI 参数和最大电流」，不含 `0x2650`；实测印证掉电不保存 ⇒ 要保护常开须每次上电显式发一次 `23 50 26 00 00 …` |

`0x2541` 的易失性对照仍是台架项（写 1 → 断电 → 读回应为 0，用 `tools/cerb_sdo_probe.py --write 0x2541:00=1`）。
