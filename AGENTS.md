# Repository Guidelines

A ROS 2 Humble workspace for a 14-DOF upper-body dual-arm robot. `motor_canfd_drive` is the protocol-neutral SocketCAN/CAN-FD driver, `motor_hardware_interface` is the `ros2_control` adapter, and `motor_canfd_sim` is the only supported simulation backend (driver → vcan → C++ simulator → Gazebo).

## Project Structure & Module Organization

- `src/<package>` — four ament packages, each with a standard layout: `src/` (implementation), `include/<package>/` (C++ headers), `config/` (YAML), `launch/`, `test/`, plus `urdf/` and `worlds/` where applicable.
- `build/`, `install/`, `log/` — generated by colcon; do not commit.
- Root PDFs — hardware manuals for the 25–30 mm drives and the RP-series CAN-FD protocol.
- Per-package `README.md` files are authoritative; start there.

## Build, Test, and Development Commands

```bash
source /opt/ros/humble/setup.bash
colcon build --symlink-install
source install/setup.bash
colcon test && colcon test-result --verbose
```

Full simulation loopback:

```bash
ros2 launch motor_canfd_sim driver_loopback.launch.py
```

- `ros2 run upper_body_canfd_gazebo ros_actions` — play a reference motion.
- `ros2 launch upper_body_canfd_gazebo hardware.launch.py left_interface:=can0 right_interface:=can1` — real-hardware bring-up.

## Coding Style & Naming Conventions

- C++17 with `-Wall -Wextra -Wpedantic`; two-space indentation.
- C++: `snake_case` for files, functions, and variables; `PascalCase` for classes; `k`-prefixed constants (e.g., `kRpMotorType`).
- Python: `snake_case`, with type hints in tests.
- Comments: Chinese for rationale, data flow, units, and safety limits; keep protocol names and ROS 2 APIs in English. Avoid mechanical per-line comments.
- No linters are configured; match the existing code style.

## Testing Guidelines

- C++: GoogleTest via `ament_cmake_gtest`, files in `src/<package>/test/test_*.cpp`.
- Python: pytest via `ament_pytest`, files in `src/<package>/test/test_*.py`, functions named `test_<behavior>()`.
- Launch-file checks use `ament_add_pytest_test` (see `motor_canfd_sim`); tests must not start Gazebo or hardware.
- Run everything with `colcon test && colcon test-result --verbose`.

## Commit & Pull Request Guidelines

- History mixes Chinese and English; prefer concise conventional subjects (`feat:`, `fix:`, `docs:`) or imperative summaries, with rationale in the body.
- Merge into `develop` via PRs that reference related issues/PR numbers; `main` is release-only.
- PRs describe the change, verification (e.g., `colcon test` results), and include launch/behavior screenshots where relevant.

## Agent-Specific Instructions

- Read `README.md` and the affected package's `README.md` before editing.
- Extend motor types via protocol strategies and YAML config; never hard-code joint counts or arm topology in the driver.
- Keep `motor_canfd_sim` the sole simulation backend; do not reintroduce Python CAN-FD simulation.
- Before hardware runs, configure CAN-FD buses (1 Mbit/s arbitration, 5 Mbit/s data) and verify zero, direction, limits, and estop per joint.
