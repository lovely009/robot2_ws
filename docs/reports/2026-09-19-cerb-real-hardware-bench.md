# 真机 CERB 台架记录（2026-09-19）：`0x2650` 读子索引纠错

> 环境：STM32H723VGT6 + ST-LINK/V2 烧录 + CANable2 SLCAN（`/dev/ttyACM1`，
> `b158aa7`）+ **四台真实 CERB 驱动器**（FDCAN1，id 1–4）；micro-ROS agent 走
> `/dev/ttyACM0`。**本次启用真机**，不再是九节点模拟器。
> 固件基线 `d1e5445`（工作树改动未提交，见文末 diff 清单）。
> 判据：设备参数初始化定论（`EVENT_DEV_INIT` + `system.last_error`）与总线上
> 的 SDO 字节序列。

## 拓扑与稳态

- 四台真机全部发现并绑定型号：id 1 = `cerb_r58_101`，id 2–4 = `cerb_r48_101`；
  `bus_index` 全 0（FDCAN1）。
- 稳态计数器：`rx_frame_count` 81,916；`decode_error_count` / `unknown_frame_count` /
  `config_rejected` / `event_dropped` / `tx_dropped` / `p0_retry` / 三条 `ring_drop`
  **全 0**；`heap_free` 12,324 B（`PARAM_BRIDGE_MAX_PARAMS = 176`）。
- 固件体量：RAM 225,108 B / 577,536 B（PlatformIO 口径 39.0%；RAM_D1 口径
  225,108 / 327,680 = 68.7%），Flash 242,452 B（23.1%）。
- 总线：FDCAN1，仲裁 1 Mbps / 数据 5 Mbps，CAN FD+BRS；SLCAN `C`→`S8`→`Y5`→`O`。

设备侧回读真值（只读 SDO，逐台）：

| `0x607D:02` 位置上限 | 32768 cnt | 32768 | 32768 | 32768 |

| `0x2541:00` 方向 | 0 (CW) | 0 | 0 | 0 |

## 发现（阻塞级，已修）：`0x2650` 的读子索引写错，全部 CERB 永远无法使能

**现象**：四台真机 `conflict: true`、`lifecycle = 7`（`CONFIG_CONFLICT`）、
`unified_fault_code = 6`（`DEV_PARAM`），`system.last_error = **41**`（回读不成功）。
四台**没有一台**能到 `DEV_INIT_OK`，因此**没有一台能被使能**。

**证据链（三条互相独立，全部指向同一处）**：

1. **总线抓包（修前）**：板子对 `0x2650` 发的是**子索引 0x01** 的读，设备明确拒绝：

   ```
   0x601 REQ  40 50 26 01 00 00 00 00      ← upload 0x2650:01
   0x581 ABORT 80 50 26 01 11 00 09 06     ← 中止码 0x06090011「子索引不存在」
   ```

   同轮里 `0x607D:01/:02`、`0x6080`、`0x2538` 都是正常应答——
  只有安全槽这一阶段 abort，于是整条 `REFRESH_PARAMS` 以 `UNCONFIRMED` 收尾，
   三次退避后定论 `UNVERIFIED`。

2. **只读探针直问真机**（新工具 `micro_ros_agent/tools/cerb_sdo_probe.py`，只发
   `0x40` 上传请求）：四台上 `0x2650:00` **可读（值 = 1）**，`:01` / `:02` 一律
   ABORT `0x06090011`。手册的写命令 `23 50 26 00 01 …` 里 `00` 才是子索引，
   早期实现把后面的数据字节 `01` 当成了子索引。

3. **`reason` 语义收敛**：`EVENT_DEV_INIT` 的 `UNVERIFIED`（reason=4）与
   `MISMATCH`（reason=3）是两回事；此前的位图恒为 0，改后能直接点名不一致槽位
   （见下）。这条区分正是排查的关键。

**根因的根因——为什么 host 与模拟台架抓不到**：模拟器 `fdcan_motor_sim.py` 与
host 测试都把该对象建模在 `(0x2650, 0x01)`，即**照固件的假设建模，而不是照对端建模**。
"固件问什么、模拟器答什么"，两个自动化层**结构上不可能**发现这个错。真机是唯一的
判据来源。

**修复**：`lib/motor_protocol/src/cerb_adapter.c` 的 `CERB_SUB_SAFETY_PROTECT`
`0x01` → `0x00`；同步改模拟器（`(0x2650, 0x00)`，并把未知子索引的 abort 码补成
真机的 `0x06090011`）与 host 测试的镜像表（`kDevSub` 等三处）。19 个 host 测试全绿。

## 修后复测（判据）

烧板后：

| 观测量 | 修前 | 修后 |
|---|---|---|
| `system.last_error` | **41**（回读不成功） | **40**（值不一致） |
| `EVENT_DEV_INIT` reason | 4 `UNVERIFIED`（位图 0） | **3 `MISMATCH`，位图 12** |
| 总线上 `0x2650` 读 | `40 50 26 01` → ABORT | **`40 50 26 00` → `43 50 26 00 …01`** |

位图 **12 = 0b1100 = 槽 2（`0x6080` 最大转速）| 槽 3（`0x2538` 峰值电流）**：
位置限位两槽一致，**安全槽与方向槽已成功回读并参与比对**（这正是修复生效的判据——
位图只有在六个槽全部到齐时才会给出 `MISMATCH` 而不是 `UNVERIFIED`）。

剩下的不一致**不是缺陷**：W25 记录还是 9-18 模拟器基线（600 RPM / 1000 mA），
真机是 3325 RPM / 5000–10000 mA。属**记录陈旧**。

**已按 owner 决定结案（同日）**：以**设备为准重新基线**记录——`storage_projection`
在 `dev_raw_present` 有位的槽上取设备原值落盘，所以顺序是
`system.refresh ×4`（把设备真值读进 dev_raw）→ `system.save`（重基线落 Flash）
→ 复位。复位后四台全部 `conflict: false`、`unified_fault_code: 0`、
`lifecycle: 3`（`READY_DISABLED`）、`last_error: 0`，`EVENT_DEV_INIT reason = 2`（OK，位图 0）。
**注意手动 `system.refresh` 的一个坑**：`dev_read_attempts` 只在上电发现时清零，
累计到 3 之后，任何一次失败的 refresh 都会**立即**定论 UNVERIFIED（不重试），
事件位图随即变成 63（全槽缺失）——那不是"六项都不一致"，而是"这次一条都没读到"。

## 安全观察（需 owner 确认口径）

四台真机 `0x2650:00 = 1`，按手册语义即**看门狗 + 限位保护处于关闭状态**。
CERB 两个型号的 `capability_flags` 都是 `CAP_LIMIT_DEVICE_SIDE`（固件**没有**软限位
兜底），因此这四台的关节限位**当前没有任何一层在执行**，且帧间隔 >500 ms 的
设备侧自锁也不生效。收尾前应确认这是台架的有意设置，而不是出厂默认。

## 追加：保护开关（`0x2650:00`）可写 + DTCM 堆再平衡（同日）

**新增写通道**：`0x2650:00` 从只读变可写，参数项 `m<id>.limit_protect`
（**正向语义 1 = 保护生效**，设备原值 0），SDO 写 + 读回核验、**不跟 `0x2539`**
（手册没给该对象的保存码），仅未运动时受理，写后记录自动同步。真机实测：

```
0x602 REQ  23 50 26 00 01 00 00 00   ← m2.limit_protect=0 下发
0x582 RSP  43 50 26 00 01 00 00 00   ← 读回核验通过
CONFIG_RESULT reason=0；四台 conflict: false；last_error=0
```

**容量问题与解法（本轮的关键发现）**：逐电机参数使每台从 4 项变 5 项，
`(176−10)/4 = 41` 台掉到 `(176−10)/5 = 33` 台，够不到实际部署的 ~40 台。
算账发现两条硬事实：

- 每槽实测 **328 B**；堆池 = 整个 DTCM 减 8 KiB 主栈 = **120 KiB**
  （`0x20000000 → _estack−8 KiB`，DTCM 总共 128 KiB）——**池子不可能再扩**。
- FreeRTOS 用 `heap_useNewlib_ST`，`pvPortMalloc` 与 `malloc` **共用这一个池**，
  任务栈也从中分配；已用 ~110.5 KB = 任务栈 44 KB + 参数槽 57.7 KB + micro-ROS ~7 KB。

解法是**搬走占用**而不是扩池：`micro_ros` 任务栈（32 KiB，最坏路径仅 ~4.4 KB）
改 `xTaskCreateStatic` 落到 RAM_D1 的 `.bss`，`PARAM_BRIDGE_MAX_PARAMS` 176 → **224**
（覆盖 42 台）。实测 `heap_free` **12,328 → 29,748 B**，稳态三次读数一致，
`last_error=0`，参数面 4 台 × 5 项全部注册。`motor_rt` 栈保持动态分配、继续在
0-wait DTCM 上；`micro_ros` 不实时，挪到带 D-cache 的 AXI SRAM 无影响。

**仍开放**：40 台规模 + 长时间运行的 `heap_free` 稳态最低位（本板只有 4 台）。

### 实测：开保护的自锁风险（假设未成立）

1 号机开到保护（设备值 `1` → `0`）后，**停掉 micro-ROS agent**（板子不再发
SYNC，也不发任何控制帧），静置 5 秒——远超手册「看门狗数据帧间隔要小于 500ms，
否则电机自锁」的窗口。结果：

| 观测量 | 停发 5 秒后 |
|---|---|
| 周期反馈 `0x301` | **仍在 12B 上报**（位置 20.66°，速度 0，电流 1 mA）|
| `data[11]` bit5 故障位 | **0**（无故障）|
| SDO 读 `0x6077` 力矩传感器 | 仍应答（值 0）|

即**「无命令 → 自锁」没有在开保护后复现**。两种解释都还成立：周期上报本身在喂
看门狗，或本设备看门狗实现与手册描述不同。**注意这是单机、空载、静态的观察**
——不足以证明带载运动中也安全。

### `0x2650:00` 对象语义（经 owner 手工核实，SLCAN 复现）

| 操作 | 帧 | 说明 |
|---|---|---|
| 读 | `40 50 26 00 00 00 00 00` | 反馈 `43 50 26 00 **0x** 00 00 00`，`0x` 即当前状态 |
| 开启保护 | `23 50 26 00 **00** 00 00 00` | 看门狗 + 限位保护生效 |
| 关闭保护 | `23 50 26 00 **01** 00 00 00` | 关闭 500 ms 看门狗及限位保护 |

官方 PR0002 §4.6 只列了「关闭」一条；**开启 = 数据字节写 `00`**，读用标准
`40`+索引+子索引，与其余对象同形。实测复现（node 1）：

```
读:   40 50 26 00 00 00 00 00
反馈: 43 50 26 00 01 00 00 00   → 1 = 关闭（写前，四台一致）
写:   23 50 26 00 00 00 00 00
应答: 60 50 26 00 00 00 00 00
读回: 43 50 26 00 00 00 00 00   → 0 = 开启
```

**TBD-CONFIG-02 的读部分据此收尾**：读子索引 = `0x00`；
`:01`/`:02` 一律 ABORT `0x06090011`（子索引不存在）。

### 实测：`0x2650:00` **掉电不保存**（最终结论）

| 节点 | 写前 | 操作 | 掉电重上后 |
|---|---|---|---|
| **1** | `1`（关闭）| 写 `23 50 26 00 00 …` → 应答 → 读回 `0`（开启）| **`1`（回退）** |
| 2–4 | `1` | 无 | `1`（对照）|

单变量对照：唯一被写过的那台回退，未碰的三台不变。

**`0x2539` 保存码对 `0x2650` 无效**——官方 §4.11 明确码 `1` =
"将写入的 **PI 参数和最大电流**保存到 Flash"，覆盖面不含保护开关；实测也印证
（发过码 1 后掉电，保护开关照样回退）。

**结论**：`0x2650` 是**易失**设置，每次上电回到上电初值。台架四台上电初值均为
`1`（关闭）。若上层要求"保护必须开着"，**必须每次上电显式发一次**
`23 50 26 00 00 …`，不能指望设备记住。

> 过程教训：本节早先写过"手册没给开启/读命令""无持久化手段""读语义无依据"——
> 那是把"**文档没列**"当成了"**不存在**"。对象语义后由 owner 手工核实、SLCAN 复现。
> 涉及本对象的结论此前都带这个偏差，已一并订正。

### 顺带发现（既有缺陷，未修）：掉电会残留参数面的在飞标记

台架复测时撞到一个**既有边界**：参数面每台字段用 `PARAM_REQUEST_TAG` 的在飞
标记（`MotorSlot.outstanding[]`）挡住影子同步，标记**只在收到对应
`CONFIG_RESULT` 时清除**。掉电/复位会让事务半途夭折，标记**永久残留**——此后
该字段的影子同步被 `sync_slot_from_view` 无限跳过，参数面永远显示旧值。

复现路径：写 `m1.limit_protect=1`（事务成功、`reason=0`）→ 断驱动器电 →
设备回退、上电判 `conflict` → 但参数面 `m1.limit_protect` 卡在旧值 `0.0`，
连 `system.refresh` 也刷不动（`refresh` 只置 `g_force_resync`，而该字段仍被
`outstanding` 挡着）。**对同名字段再写一次同一个值**即可清标记并恢复。

影响面：不限保护开关——任何走参数面的字段（限值四项同样）在"事务在飞时掉电"
后都会这样。**未修**：修法是在发现/重连（`dev_read_done` 转好）时清空该台的
`outstanding`，或在 `sync_slot_from_view` 里对"在飞但内核结论已变"的字段放行。
留给 owner 决定。
